最近 Super Agent 挺火的，我也去看了看相关的介绍。说实话，看完之后，我暂时没有那么看好。

## 先看看 Agent 的工作方式

最开始，我们接触 AI 的方式很简单：问一个问题，模型回答一个问题。后来模型会先进行推理，再给出回答；再往后，大家开始把多个步骤串成工作流，一个节点接着一个节点运行，最后把结果返回给用户。

接着就是我们现在比较熟悉的 **Agent Loop**。以 Claude Code 为例，你给它一个任务，它会根据当前情况决定下一步：是读文件、调用工具、继续处理，还是直接告诉你结果。

任务复杂的时候，它也可以把部分工作交给其他 Agent 去处理，再根据返回的信息继续往下做。这里的 Agent 也可以理解成主流程能够调用的一种能力。

当然，这些方式并不是谁出来了就完全取代前面一种，不同任务依然可能适合不同的工作方式。

![从问答到 Agent Loop 的工作方式示意](/posts/deepseek-super-agent/agent-evolution.svg)

## Super Agent 的双层架构

如果把一个复杂任务想成开公司，主 Agent 就有点像老板，下面有很多负责干活的员工。

问题来了：如果所有员工遇到事情都直接找老板汇报，事情一多，老板就得不断切换注意力。这个问题怎么解决？Super Agent 的思路，是在中间加一层“总监”，也就是**路由层**。

![Super Agent 路由层与 Worker 会话示意图](/posts/deepseek-super-agent/architecture.png)

图里左边就相当于老板在派活，中间的 Router Layer 相当于总监，负责接收任务、安排工作；右边就是具体干活的 Worker。

拿产品部门打个比方：老板把需求交给产品总监，总监再安排下面的人去做。员工做完先给总监看，总监觉得不合适，就让员工继续修改；等整理得差不多了，再把结果汇报给老板。

这样一来，老板就不用直接处理每个员工的所有细节了。至于具体怎么分派、Worker 之间能不能进一步分层，还得看实际实现和配置，不能只看一张架构图就下结论。

## 异步并行：听起来很厉害，但也带来新问题

第二个重点是**异步并行**。

就拿我用 Claude Code 的一次任务来说，下面这张图里，它先安排看清表结构和之前换编号的做法，然后复制新编号的待发布行，再用客户端检查这一行，最后等我确认后发布并回读。

这几个步骤前后是有关系的：先弄清楚怎么做，才能复制；复制好了才能检查；检查之后，还要等我确认。整个过程给我的感觉就是一步接着一步往下走。Claude Code 也能在合适的场景下并行处理任务，具体还是要看任务之间有没有依赖。

![Claude Code 分步骤处理任务](/posts/deepseek-super-agent/claude-code-steps.png)

Super Agent 想探索的，是让多个 Worker 更自然地同时处理不同的事情。就像总监收到任务之后，把能拆开的工作分给团队成员，大家同时开工。

听起来确实很美好，但我第一反应也是：**人一多不就搞乱了吗？**

有些事情可以同时做，有些事情却有先后关系。第一步的结果没出来，第三步可能根本没法开始。如果多个 Worker 都在处理相关内容，还要考虑怎么协调、怎么汇总，以及它们的工作会不会互相影响。

说到任务之间的依赖关系，我也有点好奇：Super Agent 后面会不会继续沿用 DeepSeek Harness 原来那套 DAG 机制，来安排这些任务的先后顺序？

## 架构更复杂，就一定更好用吗？

这也是我最大的疑问。

如果一个新的 Agent 架构引入了路由、多 Worker、异步并行和任务依赖管理，那它最后应该在某些任务上体现出价值。比如做一个 Web 项目时，它能不能更好地理解需求、更稳定地完成任务，或者在复杂任务上明显提高效率？

对我来说，最重要的还是**能不能让 Vibe Coding 的体验变得更好**。

比如我只需要把想法和需求讲清楚，它就能更好地安排任务、处理前后依赖，遇到问题及时告诉我，最后交付的结果也更符合预期。要是这些地方真的有提升，那架构复杂一点，我觉得也值得。

但如果架构升级了，实际用起来却没有明显区别，甚至还要花更多时间协调和排查，那我可能还是会选择自己用得顺手的工具。

基于我现在的感受，我觉得暂时没必要把架构搞得这么复杂。像 Claude Code 这种相对简单的思路，对我来说就已经够用了，而且用起来的体验也挺好。

先看看就行。
